# SCOPE — что входит в демо

Заполнено 23.09, 13:40. Больше не расширяем.

## Задача
- Трек и название задачи: 06 «Креативные индустрии» · «Умный подбор подрядчиков» (#79-lite), владелец Firebird.
- Суть (дословно): «Сервис принимает параметры заказа и возвращает до 3 карточек подрядчиков, у каждой — объяснение, почему этот подрядчик здесь. Ценность в объяснении, а не в сортировке.»
- Приоритет жюри (дословно): «качество объяснений > честная обработка редких, занятых и пустых категорий > скорость > интерфейс».
- Критерии оценки из ТЗ (дословно):
  1. Соответствие задаче и работоспособность — 25
  2. Техническая реализация (подход, архитектура, AI/agentic AI, соответствие реализации заявленной логике) — 25
  3. README и воспроизводимость — 25
  4. Ценность и применимость решения — 15
  5. Потенциал развития и оригинальность подхода — 10
- Definition of Done (дословно, проверяется вживую):
  - ответ до ~10 секунд;
  - «Объяснения не взаимозаменяемы: если стереть имена, карточки одного запроса нельзя перепутать между собой»;
  - повторный запуск с теми же параметрами — тот же порядок;
  - один запрос на две разные даты — разная выдача, и в объяснении видно, что дело в занятости;
  - минимум три запроса: плотная категория на осеннюю дату (Ведущий 15 / Фотограф 12 / Банкетный зал 8), редкая категория (по 3 профиля), запрос без результата;
  - пустой результат объяснён словами;
  - команда объясняет жюри, что происходит в пайплайне.

## Big idea — «Подбор с доказательствами: сервис знает, на что смотреть»
Боль (опыт Ивана): все подрядчики похожи, описаниям не верят, заказчик не знает, на что смотреть.
1. **Один раз заранее (офлайн-скрипт обогащения):** агент читает каждое описание и выделяет специализацию и проверяемые признаки (для кого работает, масштаб, стиль, чем отличается). Результат сохраняется в данные проекта и коммитится; без ключа всё работает на нём. Пути уточняются по выбранному каркасу.
2. **На каждый запрос:** агент формулирует «на что смотреть именно здесь» (2–3 критерия под тип мероприятия, категорию, длительность, язык) → код фильтрует и ранжирует → агент объясняет каждую карточку ПО ЭТИМ ЖЕ критериям, опираясь только на факты → код сверяет каждый факт с данными (✓ проверено). Фразы из самопрезентации — нейтрально, серым: «со слов подрядчика».
3. **Скорость и детерминизм по построению:** тяжёлая работа сделана заранее, в запросе — код + один короткий вызов модели, ответ кешируется.
4. **Два экрана:** витрина заказчика (3 карточки, «на что смотреть», понятный исход) и рабочее место менеджера площадки (таймлайн пайплайна, воронка отсева, проверка фактов, сравнение с другой датой).

Питч: «Каталог говорит “вот 30 ведущих”. Мы говорим “вот на что смотреть, вот 3 — и вот доказательство каждого слова”».

## Один сценарий
`город, дата, тип мероприятия, категория, бюджет (+ длительность, язык)` → `фильтр по фактам → ранжирование → объяснение каждой карточки агентом → проверка объяснений` → `до 3 карточек с объяснениями + строка «почему столько» + явный исход`

## Финальный экран — что увидит эксперт
- `/` витрина заказчика: строка «На что смотреть: …», до 3 карточек (имя, категория, город, цена, 1–2 предложения по этим критериям, факты с ✓, бейджи synthetic / цена проставлена), плашка исхода и «почему меньше трёх».
- `/manager` рабочее место менеджера: тот же запрос + таймлайн шагов, воронка отсева («10 → 9 свободны → 8 берут корпоратив → 6 в бюджете»), проверка фактов по каждой карточке, кнопка «сравнить с другой датой».

## Шаги (от финального экрана назад)
1. **Ответ UI:** исход (`found` / `no_category_in_city` / `all_filtered_out`) + до 3 карточек + сводка отсева.
2. **Проверка объяснений (код + LLM-критик):** нет общих фраз из стоп-листа, в каждом объяснении есть ≥1 конкретный факт (цена/формат/язык/часы/описание), объяснения разных карточек не совпадают по смыслу. Не прошло — один повтор, затем объяснение-шаблон из фактов.
3. **Объяснение (агент):** на вход — запрос + факты кандидата + чем он ОТЛИЧАЕТСЯ от двух других (считает код). Выход — схема `{ id, reason, facts_used[] }`. Температура минимальная, результат кешируется по хешу запроса → тот же запрос = тот же текст.
4. **Ранжирование (код, детерминированно):** очки за запас по бюджету, совпадение языка, запас по часам, явный формат, релевантность описания формату; ничья → по `id`.
5. **Фильтр (код):** город → категория → свободен в дату (`busy_dates`) → формат → бюджет (`price_from_kzt ≤ бюджет`) → язык (если задан) → длительность ≤ `max_hours` (`null` = не ограничен). Считаем, сколько отсеяно на каждом шаге и по какой причине → отсюда исход и строка «почему меньше трёх».
6. **Данные:** CSV организаторов → JSON в данных проекта + проверка схемы при загрузке (пути уточняются по выбранному каркасу).

## Где здесь агент, а где обычный код
- Агент (нужно суждение): объяснение «почему этот подрядчик» по смыслу описания и фактам; критик объяснений (взаимозаменяемость, общие фразы); человеческий текст для пустого/неполного результата.
- Обычный код (детерминированно): фильтр, занятость, бюджет, ранжирование, порядок, классификация исхода, подсчёт причин отсева.
